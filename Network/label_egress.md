Kubernetes Workload-Based Egress IP POC with Cilium
This lab demonstrates that Kubernetes workloads can be classified using labels and assigned deterministic outbound source IP addresses with Cilium Egress Gateway, independently of the worker node on which the pods run.
Goal
The production requirement behind the POC is:
Pods must remain free to run across Kubernetes worker nodes.
Workloads are divided into logical groups.
Group A must leave Kubernetes through one predictable source IP/range.
Group B must leave Kubernetes through another predictable source IP/range.
The external/customer network must be able to distinguish the groups by source IP.
The solution should not depend on pinning application pods to particular nodes.
The POC proves the core mechanism:
```text
Workload label             Source IP seen by destination

egress-group=a      --->   10.193.226.200
egress-group=b      --->   10.193.226.201
no egress policy    --->   normal node SNAT
```

Kubernetes Cluster
The cluster contains:
```text
1 x control-plane
1 x worker
Kubernetes v1.37.1
containerd
Cilium 1.20.2
```
The cluster deliberately runs without kube-proxy, because Cilium is configured for kube-proxy replacement.
Initialize the control plane
A pod CIDR was supplied to kubeadm:
```bash
POD_IP_RANGE="192.168.0.0/16"

sudo kubeadm init \
  --pod-network-cidr="${POD_IP_RANGE}" \
  --skip-phases=addon/kube-proxy
```
Configure kubectl as instructed by kubeadm:
```bash
mkdir -p "$HOME/.kube"
sudo cp -i /etc/kubernetes/admin.conf "$HOME/.kube/config"
sudo chown "$(id -u):$(id -g)" "$HOME/.kube/config"
```
Join the worker using the `kubeadm join` command generated by `kubeadm init`.
Before installing a CNI, the expected state is:
```text
control-plane   NotReady
worker          NotReady
CoreDNS         Pending
```
There should be no kube-proxy pods:
```bash
kubectl get pods -n kube-system
```
Install Cilium
Cilium was installed using Helm with:
kube-proxy replacement
BPF masquerading
Egress Gateway support
Set the API server information:
```bash

### Dont use
API_SERVER_IP=10.193.226.184
API_SERVER_PORT=6443
CILIUM_VERSION=1.20.2
```
Install Cilium:
```bash
# Cilium configuration
API_SERVER_IP=$(hostname -I | awk '{print $1}')
API_SERVER_PORT=6443
CILIUM_VERSION=1.20.2

echo "Kubernetes API server: ${API_SERVER_IP}:${API_SERVER_PORT}"

# Install Cilium
helm install cilium oci://quay.io/cilium/charts/cilium \
  --version ${CILIUM_VERSION} \
  --namespace kube-system \
  --set kubeProxyReplacement=true \
  --set k8sServiceHost=${API_SERVER_IP} \
  --set k8sServicePort=${API_SERVER_PORT} \
  --set egressGateway.enabled=true \
  --set bpf.masquerade=true
  
```
Wait for the cluster:
```bash
kubectl get pods -A
kubectl get nodes -o wide
```
Both nodes should become `Ready`.
Verify that kube-proxy is absent:
```bash

```
The lab showed only:
```text

cilium-envoy
```
Verify Cilium:
```bash

```

Although kubeadm was initialized with:

For example:
```text

app-b       10.0.0.234
curl-test   10.0.0.70
```
This was acceptable for the POC.

Cilium Egress Gateway Policies
Create `egress-policies.yaml`:
```yaml
apiVersion: cilium.io/v2
kind: CiliumEgressGatewayPolicy
metadata:
  name: egress-group-a
spec:
  selectors:
    - podSelector:
        matchLabels:
          egress-group: a

  destinationCIDRs:
    - "10.193.226.1/32"

  egressGateway:
    nodeSelector:
      matchLabels:
        egress-gateway: "true"
    egressIP: 10.193.226.200
---
apiVersion: cilium.io/v2
kind: CiliumEgressGatewayPolicy
metadata:
  name: egress-group-b
spec:
  selectors:
    - podSelector:
        matchLabels:
          egress-group: b

  destinationCIDRs:
    - "10.193.226.1/32"

  egressGateway:
    nodeSelector:
      matchLabels:
        egress-gateway: "true"
    egressIP: 10.193.226.201
```
Apply:
```bash
kubectl apply -f egress-policies.yaml
```
Expected:
```text
ciliumegressgatewaypolicy.cilium.io/egress-group-a created
ciliumegressgatewaypolicy.cilium.io/egress-group-b created
```
List the policies:
```bash
kubectl get CiliumEgressGatewayPolicy
```

What the POC Proves
The POC demonstrates that:
Application pods do not have to be pinned to dedicated Kubernetes worker nodes.
Kubernetes labels can classify workloads into egress groups.
Cilium Egress Gateway policies can select traffic based on those workload labels.
Different workload groups can use different deterministic source IP addresses.
Multiple workloads running on the same worker node can present different source IPs to an external destination.
Workloads not matching an Egress Gateway policy continue to use normal node SNAT behavior.
Conceptually:
```text
                   SAME Kubernetes worker
                           |
             +-------------+-------------+
             |             |             |
           app-a          app-b       ordinary pod
       egress-group=a egress-group=b       |
             |             |               |
             +------ Cilium Egress --------+
                    Gateway logic
             |             |               |
             v             v               v
       10.193.226.200 10.193.226.201 10.193.226.189
             |             |               |
             +-------------+---------------+
                           |
                           v
                   Customer network
```
This proves the core Kubernetes requirement:
> **The outbound network identity can be determined by workload classification rather than by the Kubernetes node on which the application pod happens to run.**
Production Considerations
This POC proves the Kubernetes/Cilium mechanism. A production implementation still requires network design with the infrastructure/network team.
Topics include:
Which nodes are designated as egress gateway nodes.
High availability and gateway failure handling.
Provisioning of egress IP addresses on gateway interfaces.
Routing of those addresses in the surrounding network.
Firewall rules and allowlists.
Whether each workload group receives a single IP or a broader network-side NAT design.
Gateway capacity and performance.
Persistent configuration of secondary interface addresses.
Upgrade and operational procedures.
The commands:
```bash
sudo ip addr add 10.193.226.200/24 dev ens3
sudo ip addr add 10.193.226.201/24 dev ens3
```
are appropriate for this lab but are not persistent production network configuration.
Similarly, the POC demonstrates deterministic egress IP selection. Requirements involving entire NAT address ranges should be designed together with the production network architecture rather than inferred solely from this two-IP lab.
